# LXC Updater

Web UI that runs in a Proxmox LXC and manages updates for other containers on the node — including ones installed with [Proxmox VE Helper-Scripts](https://github.com/community-scripts/ProxmoxVE) that normally require typing `update` in the CT console and answering prompts.

## Install on Proxmox (one line)

Run this **on the Proxmox host shell** (Datacenter → node → Shell), not inside a guest.

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/greir-hull/lxc-update-manager/main/install.sh)"
```

That `install.sh` is **self-contained** (app sources are embedded). The public mirror is [github.com/greir-hull/lxc-update-manager](https://github.com/greir-hull/lxc-update-manager); day-to-day development also lives on Origin at [cursor.com/codebase/greir-hull/lxc-update-manager](https://cursor.com/codebase/greir-hull/lxc-update-manager).

### From a local checkout on the host

```bash
bash install.sh
# or: bash install/proxmox-ve.sh
```

`install.sh` is generated by `bash scripts/build-one-line-installer.sh` (re-run after you change app code you want baked into the one-liner).

## Updating later (no full reinstall)

You do **not** need to re-run the Proxmox host installer for app changes. Inside the LXC:

```bash
pct enter <CTID>
update
```

That pulls the latest code from GitHub, rebuilds, and restarts `lxc-updater`. Before changing the app tree it snapshots `/opt/lxc-updater` to a temp backup under `/var/tmp`; if the download, build, or service start fails, it restores that backup and restarts the previous version. Settings, jobs, automations, and API keys under `/opt/lxc-updater-data` are never rolled back. You only need a full host reinstall when changing CT hardware (disk/CPU/network) or recreating the guest.

The installer fully provisions the guest, similar to community helper scripts:

1. Prompt for **Default** or **Advanced** settings (CTID, storage, CPU/RAM/disk, bridge, IP)
2. Create a **Debian** LXC from the official template and wait for network
3. Inside the CT (`install/in-container-setup.sh`):
   - `apt update` / `dist-upgrade`
   - base packages (curl, git, build tools, chrony, locales, python3, …)
   - locale `en_US.UTF-8`, timezone (from the host), MOTD
   - **Node.js 22** via NodeSource
   - build the app into `/opt/lxc-updater`, enable `lxc-updater.service`
   - install console **`update`** and **`lxc-updater-passwd`**, generate SSH client key for `pct exec`
4. Optionally authorize that key on the Proxmox host

Then open `http://<CT-IP>:3847`, create a login password on first visit, turn off Mock mode, and add your Proxmox API token.

| Env var | Purpose |
| --- | --- |
| `LXC_UPDATER_REPO` | Git URL for CT source / updates (default GitHub clone URL) |
| `LXC_UPDATER_GH_REPO` | `owner/name` used by `update` for tarball refreshes (default `greir-hull/lxc-update-manager`) |
| `LXC_UPDATER_BRANCH` | Branch to clone/update (default `main`) |
| `APP_PORT` | Web UI port (default `3847`) |
| `CTID` / `HN` / `STORAGE` / … | Non-interactive overrides for Advanced defaults |

## What it does

- Lists all LXC containers across the Proxmox cluster (multi-node)
- Detects how each CT updates: community `update` command, `apt`, or `apk`
- **Check for updates** — pending apt/apk packages, plus git remotes behind upstream for helper-script CTs; rows needing work show a red **Update available** button
- **Nodes** — separate tab for Proxmox **host** system updates (apt on each node via SSH); each cluster node is listed distinctly with its own check/update status
- **Appearance** — Light, Dark, and Ultra dark (near-black) themes; preference stored in the browser
- Runs updates from the browser (with live job logs)
- **Automations** — cron schedules that can re-check first and only update outdated CTs
- **API keys** — Bearer auth for Grok / other bots via `/api/v1/*`
- **Login** — password-protected web UI; recover or change the password from the CT console

## Login & password recovery

The first browser visit asks you to create a username and password. Later visits require sign-in. Change either under **Settings → Web UI login**. Dashboard APIs use an HTTP-only session cookie; `/api/v1/*` API keys are unchanged.

| Action | How |
| --- | --- |
| First-time setup | Open the UI and create a username + password |
| Change username/password | Settings → Web UI login, or `lxc-updater-passwd` in the CT |
| Forgot password | `pct enter <CTID>` then `lxc-updater-passwd --reset` |

```bash
pct enter <CTID>
lxc-updater-passwd --reset
```

## Automations

In the **Automations** tab, create a schedule (daily / weekly / monthly / cron). Recommended defaults:

- Check for updates before running
- Only update CTs with updates available
- Only running containers
- Optional stagger between CTs

**Run now** triggers the same path immediately.

## API keys (Grok bot)

1. Open **API keys** in the UI and create a key (copy the `lxcu_…` secret once).
2. Call `/api/v1/*` with `Authorization: Bearer lxcu_…` or `X-Api-Key: lxcu_…`.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/v1/status` | Cluster summary |
| GET | `/api/v1/containers` | List CTs (`?check=1`, `?available=1`, `?node=pve1`) |
| POST | `/api/v1/containers/check` | Probe for pending CT updates |
| POST | `/api/v1/updates` | Start CT updates (`{ "vmids": [101] }` or `{ "allAvailable": true }`) |
| GET | `/api/v1/nodes` | List Proxmox hosts (`?check=1`, `?available=1`) |
| POST | `/api/v1/nodes/check` | Probe host apt updates per node |
| POST | `/api/v1/nodes/updates` | Start host updates (`{ "nodes": ["pve1"] }` or `{ "allAvailable": true }`) |
| GET | `/api/v1/jobs` | Job history (`?status=running`) |
| GET | `/api/v1/jobs/:id` | Job detail + log |
| GET/POST | `/api/v1/automations` | List / create schedules |
| PATCH | `/api/v1/automations/:id` | Edit or `{ "runNow": true }` |

```bash
curl -s http://HOST:3847/api/v1/status \
  -H "Authorization: Bearer lxcu_…"

curl -s -X POST http://HOST:3847/api/v1/containers/check \
  -H "Authorization: Bearer lxcu_…"

curl -s -X POST http://HOST:3847/api/v1/updates \
  -H "Authorization: Bearer lxcu_…" \
  -H "Content-Type: application/json" \
  -d '{"allAvailable":true}'
```

Community-script updates work by piping configurable answers (usually `y`) into `update` over `pct exec`, so you do not need an interactive console.

## Quick start (development)

```bash
npm install
npm run dev
```

Open [http://127.0.0.1:3847](http://127.0.0.1:3847). **Mock mode is on by default** — sample containers and simulated updates, no Proxmox required.

## Manual deploy (without the installer)

1. Create a Debian LXC, install Node.js 22+
2. Copy this repo to `/opt/lxc-updater` and run `install/in-container-setup.sh`
3. Or: `npm install && npm run build && systemctl enable --now` using `deploy/lxc-updater.service`
4. Create a Proxmox API token and SSH trust from the CT to the host (user that can run `pct`)

In the UI → **Settings**:

| Setting | Typical value |
| --- | --- |
| Mock mode | Off |
| Proxmox host / port | Your node IP, `8006` |
| API token ID / secret | `user@pam!token-name` + secret |
| Exec mode | `SSH to Proxmox host → pct exec` |
| SSH host / key path | Same node, `/root/.ssh/id_ed25519` |

Data persists under `/opt/lxc-updater-data` (symlink from `data/`).

## Updating the updater CT

Inside the LXC console:

```bash
update
```

Follow the prompts (same pattern as other helper-script containers). A failed update rolls the app tree back automatically from the temp backup.

## How community-script updates work

Helper-script CTs expose an `update` command that is interactive. LXC Updater runs roughly:

```bash
pct exec <vmid> -- bash -lc 'printf "y\ny\n…" | update'
```

Answers are editable in Settings. Plain Debian/Alpine CTs without `update` fall back to `apt` / `apk` upgrades.

## Security notes

- Protect the web UI with the login password (or reset it from the CT console if forgotten).
- Treat the API token and SSH key as root-equivalent for container management.
- Bind the UI to a trusted network or put it behind SSO / reverse proxy.
- Automations can upgrade many CTs — start with a small selected set.
- Anyone with root on the updater CT can reset the UI password via `lxc-updater-passwd --reset`.
